# Джарвис Lite: подготовка переносимой сборки

## Функции панели Lite и звуки

Добавлены все шесть WAV интерфейса в allowlist сборки; новые настройки включают
ui_sounds_enabled по умолчанию. Пользовательская настройка при обновлении не
сбрасывается. В staging-lite-002 звук уже включён пользователем.

Открыты локальный журнал с поиском, текстовый чат, консоль команд/озвучки,
избранное, диагностика наличия компонентов, отдельный автозапуск Lite,
полное отключение только Lite. Консоль не обращается к Discord: она создаёт
локального Jarvis без распознавателя и пишет результат в журнал. Диагностические
print/TTS сообщения перенаправлены в stderr, чтобы не повреждать JSON-протокол.

В Tools добавлена памятка команд. Стандартные приложения используют %WINDIR%,
а не пути владельца. pywin32 и OpenCV добавлены для клавиатуры, буфера обмена
и распознавания цветов. Голосовые действия используют общий main/router/tools.
Игры и нестандартные приложения настраиваются на компьютере друга через
конструктор; авторские ярлыки/пути не копируются.

Не перенесены намеренно: Discord-управление, настройки ответов/обучение Пятницы,
Qwen, RVC, прежняя полная панель. Восстановление голосовых компонентов Пятницы
не показывается как «ремонт Lite». Проверка целостности с докачкой ещё не готова.
Автозапуск создаёт только EFREN_Lite_<идентификатор>.lnk и не удаляет основной.

## Первый вход и локальный запуск

Добавлены lite_runtime.py: собственный пароль первого входа (PBKDF2-SHA256),
проверка владения процессом по exe/командной строке/времени создания и управление
только локальным Джарвисом. Mutex панели и Джарвиса отделены по пути установки.
Lite backend больше не создаёт старую Tk-панель. Кнопки запуска доступны.
Сборщик исключает из старого исходника хеш пароля владельца; credentials в
lite-auth.json никогда не входят в список копируемых файлов.
Актуальная инструкция и границы тестирования: LITE_TESTING.md.
Заявления о заблокированном запуске ниже относятся к предыдущим этапам.

## Актуальный статус: GigaAM CPU

Lite использует `jarvis_stt_backend=gigaam-local-cpu`, `models/gigaam/v3_rnnt.ckpt`,
два CPU-потока. `gigaam_local.py` принимает PCM через VoiceListener напрямую:
без FFmpeg, временных WAV, сервера Пятницы и CUDA. Whisper больше не импортируется
на этом пути и не входит в новый список голосовых зависимостей.

В staging-lite-002 установлены torch/torchaudio 2.7.1+cpu с официального CPU index,
GigaAM из проверенного локального исходника (хеши и лицензия сохранены), checkpoint
v3_rnnt. Исходная среда GigaAM и текущая Пятница не изменялись.
Старые экспериментальные Whisper-файлы пока остаются в staging, но не используются;
при подготовке чистого релизного пакета их не включать.

Реальный тест `check_gigaam_lite.py <staging> <wav-directory>`:
6 WAV прошли путь VoiceListener → PCM/resampling → GigaAM, 1.131–2.367 с на запись.
Проверены CPU-only torch и загрузка GigaAM именно из staging. Микрофон не открывался,
команды не выполнялись. Отчёт: `runtime/gigaam-integration-test.json`.
В тесте про Доту пропало обращение; маршрутизация и wake detection ещё требуют теста.
Кнопки запуска остаются заблокированы. Пакет ещё не готов для публикации.

Ниже — история этапов; упоминания Whisper описывают ранний эксперимент.

Текущий этап — **заготовка исходников, не готовая переносимая программа**.
Не загружать staging в Releases. Рабочая установка не изменяется.

`prepare_lite.py <новая-папка>` копирует только явно перечисленные исходники,
создаёт настройки с нуля и SHA-256-манифест. Существующий каталог не перезаписывается.
Личные конфиги, темы, журналы, пароли, память, сценарии, модели и среды не копируются.
Манифест пока не подписан и не подходит как доверенный источник для обновлятора.

## Что ещё требуется перед раздачей

1. Переносимый Python и проверенный набор зависимостей: текущий WPF backend ищет Python313 у пользователя.
2. Убрать обязательные импорты Discord/STT worker и Ollama из Lite-пути запуска.
   Пока вспомогательные исходники включены только для сохранения зависимостей.
3. Lite-режим интерфейса и обработчика: скрыть и запретить Discord/Qwen,
   отделить mutex, PID и порты от полной версии. Отключённых настроек недостаточно.
4. Проверить все пути: не допускать обращений к исходной установке и диску автора.
5. Подготовить CPU-распознавание и Piper, проверить лицензии и условия распространения
   каждой модели и библиотеки. Модели пока не скачиваются автоматически сборщиком.
6. Первый запуск без авторского пароля; устройства Windows по умолчанию.
7. Проверить в чистом окружении без Python, CUDA, Voicemeeter и оригинальной папки.
8. Только после этого — архив, подпись манифеста, GitHub Release и ссылка на сайте.

Тесты: `python -m unittest discover -s distribution -p test_prepare_lite.py -v`.

## Встроенный Python (этап 2)

Панель и Python-обработчики сначала ищут `runtime/python/python.exe`.
Наличие `lite-build.json` запрещает fallback к системному Python.
Полная версия без этого маркера сохраняет прежний резервный путь.

`add_python.py <staging> <чистый-CPython-3.12>` добавляет среду отдельно,
без пользовательских site-packages и startup hooks. Это вспомогательный сборщик
для проверенной uv-среды разработчика, не универсальный установщик Python.
В `staging-lite-002` для проверки панели установлен Pillow 12.3.0.
Голосовые зависимости пока не устанавливались.

`check_python.py <staging>` проверяет импорт backend, Tk, Pillow, выбор Python
и отказ неавторизованной команде. PATH очищен от пользовательского Python,
PYTHONHOME/PYTHONPATH удалены, user-site отключён. Голос, Discord и команды
не запускаются. Это не замена тесту на чистой Windows.

Манифест исходников создаётся до установки среды; он не является манифестом
всей готовой сборки. Перед публикацией потребуется новый подписанный манифест.

## Голосовые зависимости (этап 3)

В staging-lite-002 установлены пакеты из requirements-voice.txt.
Whisper-модель пока НЕ упакована, Piper и голос пока НЕ упакованы.
Нельзя считать эту папку готовой офлайн-сборкой.

Lite больше не создаёт LocalLLM и не импортирует Ollama при запуске main.py.
Настройки Lite принудительно отключают Qwen и Discord при каждом чтении.
voice.py загружает friday_voice_worker только для shared-STT режима;
самостоятельный faster-whisper его не импортирует.
Для новых Lite-заготовок заданы CPU/int8, 2 потока, один worker.
При отсутствии настройки потоков поведение полной версии не меняется.

check_voice.py запускается встроенным Python с путём staging и проверяет
импорты и инициализацию, запрещая Ollama, local_llm, PyTorch и Friday worker.
Модель, микрофон, TTS и WindowsTools в тесте заменены заглушками: реальная
скорость, качество речи и распознавание этим тестом НЕ проверяются.

## Реальный тест голосовых компонентов (этап 4)

prepare_voice_assets.py добавляет локальный Piper по списку файлов (без личных
WAV) и скачивает Systran/faster-whisper-base с фиксированием ревизии. Токен HF
не используется. Это подготовка для разработки, а не разрешение на публикацию.
В staging-lite-002 теперь присутствуют и модель распознавания, и Piper/Ruslan.

check_voice_real.py генерирует нейтральную фразу и распознаёт её на CPU/int8,
2 потока, offline-режим загрузки модели. Звук не проигрывается, микрофон не
записывается, команды не выполняются. Отчёт: runtime/voice-test.json.
Первый тест: 4.45 с аудио, 2.66 с синтез, 1.02 с загрузка STT, 3.37 с STT.
Это замер на машине разработчика, не на Ryzen друзей.
Распознавание исказило имя и команду («Джаррес откроем в настройке»).
Тест подтверждает работоспособность компонентов, но НЕ достаточную точность.
Кнопки запуска Lite остаются заблокированы до проверки всей цепочки.

Перед распространением собрать лицензии всех бинарников Piper/eSpeak/ONNX и
моделей. Карточка голоса Ruslan указывает датасет CC BY-NC-SA 4.0:
https://huggingface.co/rhasspy/piper-voices/blob/main/ru/ru_RU/ruslan/medium/MODEL_CARD
Whisper base: https://huggingface.co/Systran/faster-whisper-base (MIT).

Архитектура общего бота владельца зафиксирована в BOT_CONNECTION.md.
